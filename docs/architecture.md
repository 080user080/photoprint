# docs/architecture.md

```markdown
# Architecture — PhotoPrint (автоматична обробка та друк)

Цей документ описує технічну структуру проєкту відповідно до
docs/PRD.md. Мета — зафіксувати, які модулі вже існують, які потрібно
додати, і як вони з'єднуються, щоб нові джерела/виходи/кроки обробки
можна було підключати без переписування вже готової логіки.

## 1. Центральний архітектурний принцип: Job Source / Core Pipeline / Job Sink

```
┌─────────────────────┐      ┌────────────────────────┐      ┌────────────────────┐
│   JOB SOURCES       │      │    CORE PIPELINE       │      │    JOB SINKS       │
│                     │      │                        │      │                    │
│ - Manual GUI import │─────▶│  Job Queue (спільна)   │─────▶│ - priPrinter       │
│   (є)               │      │         │              │      │   (є, core/        │
│ - Watched folder    │      │         ▼              │      │   printer.py)      │
│   (Фаза 1, план)    │      │  Confidence scoring    │      │                    │
│ - Virtual printer   │      │  (новий модуль)        │      │ (майбутні sink'и   │
│   capture           │      │         │              │      │  підключаються     │
│   (Фаза 2-3)        │      │         ▼              │      │  так само, без     │
│ - (майбутні)        │      │  processing/pipeline.py│      │  зміни pipeline)   │
└─────────────────────┘      │  (є, без змін логіки)  │      └────────────────────┘
                             │         │              │
                             │         ▼              │
                             │  Cache / manifest      │
                             │  (новий модуль)        │
                             └────────────────────────┘
```

**Контракт Job Source** — будь-яке джерело завдань зобов'язане вміти
тільки одне: покласти в спільну чергу пару (растрове зображення або
шлях до файлу + метадані походження). Джерело нічого не знає про
обробку, кеш чи друк.

**Контракт Job Sink** — будь-який вихід зобов'язаний вміти прийняти
вже оброблене зображення і зробити з ним щось (надрукувати,
зберегти, відправити). Sink нічого не знає, звідки прийшло
зображення чи як воно було оброблено.

**Core Pipeline** — усе, що між ними: черга, оцінка впевненості,
власне обробка (`processing/pipeline.py` — без змін основної логіки
на цьому етапі), кеш/дедуплікація. Не знає ні про джерела, ні про
виходи.

Наслідок для розробки: нове джерело або новий вихід — це один новий
файл-модуль, що реалізує простий контракт, без торкання
`processing/`, `batch_processor.py` чи `core/printer.py`.

## 2. Наявні модулі (без змін логіки в Фазі 1)

| Модуль | Роль | Статус |
|---|---|---|
| `core/loader.py` | Завантаження зображень (jpg/png/tiff/heic/raw) → BGR numpy | Є, без змін |
| `core/saver.py` | Збереження JPG | Є, без змін |
| `core/printer.py` | Відправка на друк (mspaint /pt, ShellExecute) | Є; Фаза 1 — прибрати залежність від змінного `printer_name`, зафіксувати priPrinter |
| `processing/*` | Класифікація документа, тіні, перспектива, контраст, різкість, білий фон тощо | Є, без змін основної логіки |
| `processing/pipeline.py` | Єдина точка входу в обробку | Є; додається виклик confidence-скорингу після `run_autofix` |
| `processing/diagnostics.py` | Метрики зображення (uniformity, blur, contrast, тощо) | Є; джерело даних для confidence-скорингу — нових метрик писати не треба, використовуємо наявні |
| `batch/batch_processor.py` | Паралельна обробка черги, RAM guard | Є; правки: формула потоків `cpu_count - 1`, ліміт RAM з GUI-налаштування |
| `gui/*` | Вікно, черга, слайдери, налаштування | Є; додається: авто-показ вікна при появі файлів у черзі перегляду, дві групові кнопки, чекбокс приховування |
| `config/app_settings.py` | Читання/запис settings.ini | Є; додаються нові поля (див. розділ 6) |

## 3. Нові модулі (Фаза 1)

### 3.1 `confidence/scorer.py` (новий)
Rule-based оцінка впевненості результату обробки. Приймає на вхід
дані, які вже повертає `pipeline.run_autofix` (список `log_entries`,
метрики з `diagnostics.DiagnosticResult`), і повертає булеве
рішення "впевнено" / "потребує перегляду" плюс, для налагодження,
причину (яке саме правило спрацювало).

Початковий набір правил (rule-based, без скорингу 0-100):
- кути перспективи не знайдені там, де очікувались (для
  bw_document/color_document);
- тип документа визначено на межі порогів класифікації
  (doc_classifier);
- залишковий blur після авто-різкості все ще нижче прийнятного
  порогу;
- залишкова нерівномірність фону (background_uniformity) низька
  після shadow_remove.

Точні пороги — не фіксуються заздалегідь у коді жорстко, а
виносяться в config, щоб можна було підлаштовувати під реальні дані
без переписування правил.

### 3.2 `cache/manifest.py` (новий)
Дисковий кеш оброблених результатів + дедуплікація.

- Ключ: SHA-256 хеш `numpy.ndarray.tobytes()` растеризованого
  вхідного зображення (той самий підхід, що вже використовується для
  RAM-кешу прев'ю в `utils/image_utils.py::_preview_cache_key`,
  перенесений на диск і на повні оброблені зображення).
- Сховище метаданих: легка SQLite-база (`cache/manifest.db`) або
  JSON-файл — конкретний вибір за простотою реалізації, не впливає
  на решту архітектури.
- Записи: хеш → шлях до кешованого обробленого файлу, час створення,
  розмір, статус (оброблено автоматично / оброблено вручну).
- Ліміт розміру — з `config` (дефолт 1 ГБ, змінюється в GUI). При
  перевищенні — видалення найстаріших записів (LRU за часом
  останнього використання).
- Логіка виклику: перед обробкою нового завдання рахуємо хеш →
  перевіряємо кеш → якщо є, беремо готовий результат і одразу
  передаємо в Job Sink (друк), минаючи і `processing/pipeline.py`, і
  confidence-scorer, і чергу ручного перегляду.

### 3.3 `queue/review_queue.py` (новий, або розширення `gui/queue_view.py`)
Черга ручного перегляду — окрема від основної черги обробки
(`BatchProcessor._files`). Наповнюється автоматично, коли
confidence-scorer повертає "потребує перегляду" **і** налаштування
поведінки (див. 3.1 в PRD, розділ 6.3) встановлено на «Запит
оператора». При інших значеннях налаштування (друк оригіналу / друк
з тим, що вдалось) ця черга не використовується взагалі — файл одразу
йде в Job Sink.

Відповідає за:
- зберігання списку файлів, що очікують рішення оператора;
- сигнал у GUI-шар про потребу показати вікно і сповіщення в треї;
- дві групові дії (друк усіх як є / друк усіх з тим, що вдалось) —
  викликають Job Sink напряму, минаючи по-файловий перегляд.

### 3.4 Watched-folder source (за потреби у Фазі 1, `sources/watched_folder.py`)
Якщо буде потрібне джерело "слідкувати за папкою" вже в Фазі 1 (для
тестування автопайплайну без ручного імпорту) — окремий модуль, що
відповідає контракту Job Source з розділу 1. Рішення про необхідність
цього конкретного джерела в Фазі 1 — за результатами перших тестів,
не є жорсткою вимогою.

### 3.5 Трей / автозапуск (розширення наявного)
- Запис у автозавантаження Windows (реєстр `Run` або ярлик
  `shell:startup`).
- Старт одразу у прихованому/трей-режимі (зараз `main.py` завжди
  показує вікно — потрібна умова запуску в фоні).
- Використання наявного `QSystemTrayIcon` для сповіщень про чергу
  перегляду (вже частково реалізовано для minimize-to-tray).

## 4. Потік виконання (Фаза 1, спрощено)

```
Нове зображення (від Job Source)
      │
      ▼
Порахувати хеш пікселів
      │
      ├── Є в кеші? ──так──▶ Взяти кешований результат ──▶ Job Sink (друк)
      │
      ні
      ▼
processing/pipeline.run_autofix()  (без змін)
      │
      ▼
confidence/scorer.py → впевнено?
      │
      ├── так ──▶ Зберегти в кеш ──▶ Job Sink (друк)
      │
      ні
      ▼
Перевірити налаштування "поведінка при низькій впевненості"
      │
      ├── "Друкувати оригінал"      ──▶ Job Sink (оригінал, без обробки)
      ├── "Друкувати з тим, що вдалось" ──▶ Job Sink (результат pipeline)
      └── "Запит оператора" (default) ──▶ queue/review_queue.py
                                              │
                                              ▼
                                     Показати GUI + сповіщення в треї
                                              │
                                              ▼
                          Оператор: ручна корекція+друк / пропустити /
                          групова дія "друк всі як є" / "друк всі з тим що вдалось"
```

## 5. Фазовий план (технічний розріз)

### Фаза 1 (поточна)
- `confidence/scorer.py`, `cache/manifest.py`, `queue/review_queue.py`
  — нові модулі.
- Правки в `batch_processor.py` (формула потоків, RAM-ліміт з
  налаштувань), `core/printer.py` (фіксований priPrinter),
  `gui/*` (авто-показ, групові кнопки, налаштування).
- `processing/*` — без змін логіки.

### Фаза 2 (дослідницький спайк, ізольовано)
- Дослідження підходу "віртуальний принтер" у Windows (port monitor
  redirection або аналог).
- Результат — прототип, що перетворює спул-завдання друку на файл
  растрового зображення на диску. Не інтегрується з Job Queue на
  цьому етапі.
- Технічні деталі реалізації драйвера — навмисно не фіксуються
  заздалегідь у цьому документі, оскільки залежать від результатів
  дослідження.

### Фаза 3 (інтеграція)
- Новий модуль `sources/virtual_printer_source.py`, що реалізує
  контракт Job Source з розділу 1, використовуючи прототип з Фази 2.
- Жодних змін у `processing/`, `cache/`, `confidence/`,
  `core/printer.py`.

### Фаза 4 (майбутнє, не деталізується)
- Модуль оцінки % покриття тонером і орієнтовної вартості — буде
  додано як ще один крок після обробки, що читає вже оброблене
  зображення (не потребує змін у Job Source/Sink контракті).

## 6. Нові налаштування (config/app_settings.py, Фаза 1)

| Ключ | Призначення | Дефолт (орієнтовно) |
|---|---|---|
| `low_confidence_behavior` | `"ask_operator"` \| `"print_original"` \| `"print_best_effort"` | `"ask_operator"` |
| `show_bulk_review_buttons` | Показувати дві групові кнопки в черзі перегляду | `true` |
| `cache_size_limit_mb` | Ліміт дискового кешу оброблених результатів | `1024` |
| `ram_usage_ratio` | Частка доступної RAM для паралельної обробки (заміна/винесення наявного `MAX_RAM_RATIO`) | вище, ніж поточні 0.6 — точне значення визначити тестуванням |
| `worker_threads` | Вже є в коді; формула дефолту зміниться на `cpu_count - 1` | `cpu_count - 1` |
| `autostart_enabled` | Автозапуск у треї при старті Windows | `true` |

## 7. Що явно НЕ входить у Фазу 1 (архітектурно)

- Жодної логіки вибору фізичного принтера — `core/printer.py` завжди
  цілиться в priPrinter.
- Жодного коду перехоплення друку — це повністю Фаза 2, ізольована.
- Жодного ШІ-модуля — залишається як майбутній крок у
  `processing/pipeline.py`, підключення без зміни контракту.
- Архів пропущених файлів — не реалізується, але дизайн
  `queue/review_queue.py` не повинен цьому заважати в майбутньому
  (просте розширення, не переробка).

## 8. Відкриті технічні питання (переносяться в adr.md по мірі вирішення)

- Формат сховища `cache/manifest.py` — SQLite чи JSON (вирішується
  на етапі реалізації, не впливає на архітектуру).
- Точні порогові значення для `confidence/scorer.py` — визначаються
  експериментально на реальних даних точки друку.
- Чи потрібен `sources/watched_folder.py` вже в Фазі 1, чи досить
  наявного ручного імпорту для тестування автопайплайну.
```
