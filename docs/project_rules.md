# Правила роботи агента (Cline) — проєкт PhotoPrint

## Загальні
- Платформа: Windows 10/11.
- Мова: Python 3.11+ (перевірити фактичну версію в наявному venv
  перед першим запуском).
- Існуючий стиль коду в проєкті: PEP8, type hints (`|` union-синтаксис
  вже використовується в наявних файлах, напр. `str | None`),
  docstrings українською мовою (як у наявних `processing/*.py`) —
  зберігати цей самий стиль і мову коментарів у новому коді.
- НІКОЛИ не хардкодити шляхи, ключі, паролі — тільки через
  `config/app_settings.py` або `.env`, якщо з'явиться потреба в
  секретах (наразі секретів у проєкті немає).

## Межі роботи з наявним кодом
- НЕ змінювати логіку модулів `processing/*` (autofix, sharpen, hdr,
  perspective, shadow_remove, color_cast, brightness_contrast,
  doc_classifier, diagnostics, white_background, deskew, text_mask,
  detail_map, shadow_highlight, pipeline) у межах Фази 1, окрім
  точково узгоджених доповнень (наприклад виклик confidence-scorer
  після `run_autofix` — тільки додавання виклику, не зміна самої
  функції `run_autofix`).
- Нові модулі з `docs/architecture.md` (розділ 3: `confidence/`,
  `cache/`, `queue/`, майбутні `sources/`) створювати як окремі
  файли/пакети, що відповідають Job Source / Job Sink контракту
  з розділу 1 `architecture.md` — не вбудовувати їхню логіку
  всередину наявних `gui/*` чи `batch/*` файлів без потреби.
- Перед будь-якою зміною наявного файлу — прочитати його цілком
  (view), а не редагувати наосліп по фрагменту з документації.
- НЕ змінювати `docs/architecture.md` без явного погодження в чаті.

## Робочий процес
- НЕ писати код, якщо не отримано прямого завдання з `TODO.md`.
- Кожен пункт `TODO.md` виконується ізольовано: один пункт → один
  git-комміт з message формату `TODO-<номер>: <короткий опис>`.
- Оновлювати `TODO.md` (позначати `[x]`) одразу після підтвердження
  людиною, що критерій "готово" виконано — не позначати самостійно
  без підтвердження.
- Якщо під час виконання пункту з'ясовується розбіжність із
  `architecture.md` або необхідність відхилення від плану — зупинитись,
  описати розбіжність у чаті і в `docs/adr.md`, чекати рішення, а не
  вирішувати самостійно.
- Раз на кожні ~5 виконаних пунктів `TODO.md` — оновити короткий
  підсумок у `docs/summary.md` (поточний стан, що зроблено, що
  залишилось), щоб не тримати весь контекст проєкту в пам'яті агента.

## Специфіка цього проєкту
- Точка друку працює з реальними клієнтами — новий код, що торкається
  `core/printer.py` або будь-якого шляху до фізичного друку, повинен
  проходити через явне тестове підтвердження людиною перед комітом
  (не автоматизувати друк-тести без нагляду).
- Будь-яка зміна дефолтних параметрів обробки (пороги confidence-scorer,
  `worker_threads`, `ram_usage_ratio`, `cache_size_limit_mb`) —
  виносити в `config/app_settings.py`, не хардкодити в коді модуля.
- Фаза 2 (дослідження перехоплення друку) — окрема ізольована робота,
  не повинна ламати чи змінювати нічого з того, що вже працює у Фазі 1.
  Прототип Фази 2 живе окремо (наприклад окрема тека `research/` або
  окрема гілка git) до моменту явної інтеграції у Фазі 3.
