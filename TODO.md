### 2.5-b — Розсинхронізація черги в ручному друці одного файлу (main_window.py)
**Проблема:** `_do_print_current` синхронізує `_processor` з чергою
лише умовно: `if self._processor.total == 0: self._processor.set_files(...)`.
Якщо процесор уже має файли з попереднього запуску (наприклад,
частково пройдений пакетний друк), а в чергу тим часом додали нові
файли — вони не потраплять у `_processor._files`, і подальший
логічний перехід по черзі (`_load_next_manual`, `current_index`)
буде посилатись на застарілий список.

**Файл:** `gui/main_window.py` → `_do_print_current`, `_sync_processor_with_queue`

**Кроки:**
- [x] У `_do_print_current` замінити умовну перевірку
      `if self._processor.total == 0: ...` на безумовний виклик
      `self._processor.sync_new_files(self._queue.get_all_paths())`.
      Головна логіка збережена: файл, відкритий через чергу
      (`_current_path in queue`), друкується напряму через
      `printer_module`; батч-режим — через `_processor.print_current()`.
      Синхронізація виконується безумовно (через `sync_new_files`,
      який не скидає `_index`).
- [x] Створено окремий метод `sync_new_files()` у `batch_processor.py`
      замість повного `set_files()`, який лише додає нові шляхи, не
      скидаючи `_index`. Підтверджено юніт-тестами
      (`tests/unit/test_batch_processor.py`), що `_processor.current_index`
      не скидається і позиція в черзі для вже надрукованих файлів не
      "губиться".
- [x] Сценарій перевірено юніт-тестом
      `test_todo_scenario_partial_batch_then_new_files`: пакетний друк
      частково пройдено (5 з 10) → додано 3 нових файли в чергу →
      `_index` лишається 5, `total` стає 13, `has_next()` — True,
      нові файли з'являються в подальшому проході черги.
- [x] Відмітити виконання.
