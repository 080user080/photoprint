Документ складено на основі повного зрізу коду проєкту (`status.md`, `processing/perspective.py`,
`processing/pipeline.py`, `gui/main_window.py`, `config/app_settings.py` та ін.).
Завдання впорядковані за пріоритетом. Кожне завдання містить: мету, файли, кроки реалізації,

## 0. Загальні правила для агента (читати перед будь-якою зміною)

1. **Архітектура не змінюється без потреби**: `gui/*` звертається тільки до `processing/pipeline.py`
   та `batch/batch_processor.py`. Жодна функція в `processing/*`, `core/*`, `utils/*` не повинна
   імпортувати щось з `gui/*`.
2. **Immutability вхідних зображень**: будь-яка функція обробки повертає **новий** масив
   (`.copy()` або операція, що створює новий буфер). Вхідний `image: np.ndarray` ніколи не
   модифікується in-place.
3. **Стиль коду**: type hints у сигнатурах, docstring українською для кожної публічної функції,
   константи (магічні числа) — на початку файлу великими літерами, логування через
   `utils.logger.get_logger(__name__)` рівнем `debug` для деталей алгоритму та `error` для винятків.
4. **Налаштування** йдуть по ланцюжку: `config/app_settings.py` (default-константа + `load`/`save`)
   → `dict settings` у `main_window` / `BatchProcessor` → елемент GUI (`controls.py` або
   `settings_window.py`) → kwargs у `processing/pipeline.py`. Будь-яка нова "ручка" має пройти
   весь ланцюжок, інакше вона буде "мертвою".
5. **Тестування**: перед і після кожної задачі запускати наявні сценарії
   `tests/scenarios/*.py` (там, де вони вже функціональні), а для нової логіки — додавати
   юніт-тест у `tests/` (директорія `tests/unit/` — створити, якщо немає) для `processing/*`
   без залежності від GUI.
6. Кожне завдання нижче — окремий комміт/PR з описом і (за можливості) скриншотом
   до/після з `tests/test_images`.

3. **Тест immutability** — створити `tests/unit/test_immutability.py`:

4. **Критерії приймання**:
   - Тест `test_immutability.py` зелений для всіх перелічених функцій.

## ПРІОРИТЕТ 2 (ВИСОКИЙ) — Часткова корекція перспективи

**Мета**: коли одна сторона документа крива, а інші три прямі — виправляти тільки криву сторону,
не деформуючи решту зображення.

### 2.1 Нова логіка в `processing/perspective.py`

Додати після `_order_points`:

```python
# Поріг "кривизни" сторони — у частках від відповідного розміру (не в пікселях!),
# бо кути повертаються у координатах оригінального (повнорозмірного) зображення.
PARTIAL_SKEW_THRESHOLD_RATIO = 0.01  # 1% від ширини/висоти документа

def detect_skewed_sides(pts: np.ndarray) -> dict[str, bool]:
    """
    pts: впорядковані [TL, TR, BR, BL].
    Повертає {"top": bool, "bottom": bool, "left": bool, "right": bool} —
    True, якщо відповідна пара кутів відхиляється від "прямої" сторони
    більше ніж на PARTIAL_SKEW_THRESHOLD_RATIO від розміру документа.
    """
    tl, tr, br, bl = pts
    width = max(np.linalg.norm(tr - tl), np.linalg.norm(br - bl), 1.0)
    height = max(np.linalg.norm(bl - tl), np.linalg.norm(br - tr), 1.0)
    thr_w = width * PARTIAL_SKEW_THRESHOLD_RATIO
    thr_h = height * PARTIAL_SKEW_THRESHOLD_RATIO
    return {
        "top":    abs(tl[1] - tr[1]) > thr_h,
        "bottom": abs(bl[1] - br[1]) > thr_h,
        "left":   abs(tl[0] - bl[0]) > thr_w,
        "right":  abs(tr[0] - br[0]) > thr_w,
    }


def apply_partial_correction(image: np.ndarray, corners: np.ndarray) -> np.ndarray:
    """
    Виправляє перспективу лише для "кривих" сторін документа.
    Якщо жодна сторона не крива — повертає копію без змін.
    Якщо всі 4 сторони криві — делегує в apply_correction (повна корекція).
    """
    pts = _order_points(corners.astype(np.float32))
    skew = detect_skewed_sides(pts)

    if not any(skew.values()):
        return image.copy()
    if all(skew.values()):
        return apply_correction(image, corners)

    adjusted = pts.copy()
    tl, tr, br, bl = 0, 1, 2, 3

    if skew["top"]:
        y = (pts[tl][1] + pts[tr][1]) / 2.0
        adjusted[tl][1] = y
        adjusted[tr][1] = y
    if skew["bottom"]:
        y = (pts[bl][1] + pts[br][1]) / 2.0
        adjusted[bl][1] = y
        adjusted[br][1] = y
    if skew["left"]:
        x = (pts[tl][0] + pts[bl][0]) / 2.0
        adjusted[tl][0] = x
        adjusted[bl][0] = x
    if skew["right"]:
        x = (pts[tr][0] + pts[br][0]) / 2.0
        adjusted[tr][0] = x
        adjusted[br][0] = x

    # dst — той самий bounding rect, що й adjusted-точки (без розтягування на весь прямокутник,
    # щоб не деформувати прямі сторони)
    dst, width, height = _compute_destination(adjusted)
    M = cv2.getPerspectiveTransform(pts, dst)
    return cv2.warpPerspective(
        image, M, (width, height),
        borderMode=cv2.BORDER_CONSTANT, borderValue=(255, 255, 255),
    )
```

> Примітка: `_compute_destination` уже існує і додає `PADDING_RATIO`. Перевірити, що він
> коректно працює і для "adjusted" точок (не лише для чотирикутника з реальної детекції).

### 2.2 Інтеграція в `processing/pipeline.py`

- Додати параметр `partial: bool = False` до:
  - `run_perspective_auto(image, partial=False)` → викликає

  `auto_detect_corners` обирає `apply_partial_correction` або `apply_correction`.

  `perspective.auto_correct(result, partial=partial_perspective)`.

## ПРІОРИТЕТ 3 (ВИСОКИЙ) — Покращення авто-детекції кутів (`processing/perspective.py`)

Поточна реалізація вже має resize→800px, AdaptiveThreshold (обидва напрямки), Canny, fallback
bounding box, перевірку площі/пропорцій, MORPH_CLOSE, padding 6%. Нижче — конкретні доопрацювання
з попереднього аналізу багів.

### 3.1 Захист fallback від "рамки фото / столу" (solidity + border-touch)

У `_try_largest_contour` та у блоці "більше 4 кутів" в `_find_quad_contour`:

- Додати функцію:
  ```python
  BORDER_MARGIN_PX = 2
  MAX_BORDER_AREA_RATIO = 0.92  # контур, що майже = всьому кадру — підозра на фон/стіл

  def _touches_image_border(cnt: np.ndarray, shape: tuple, margin: int = BORDER_MARGIN_PX) -> bool:
      h, w = shape[:2]
      x, y, bw, bh = cv2.boundingRect(cnt)
      return x <= margin or y <= margin or (x + bw) >= (w - margin) or (y + bh) >= (h - margin)
  ```
- Якщо контур торкається межі зображення **і** його площа > `MAX_BORDER_AREA_RATIO * image_area`
  — пропускати цей контур (ймовірно це фон/стіл/рамка кадру, а не документ).
- Додати solidity-перевірку (компактність форми):
  ```python
  MIN_SOLIDITY = 0.85

  def _solidity(cnt: np.ndarray) -> float:
      area = cv2.contourArea(cnt)
      hull_area = cv2.contourArea(cv2.convexHull(cnt))
      return area / hull_area if hull_area > 0 else 0.0
  ```
  Використовувати як додаткову умову у `_validate_document` (`solidity >= MIN_SOLIDITY`).

### 3.2 Адаптивний epsilon для `approxPolyDP`

Замінити одиничний `APPROX_POLY_EPSILON = 0.02` на список спроб:

```python
APPROX_POLY_EPSILONS = (0.01, 0.02, 0.03, 0.04)
```

У `_find_quad_contour` для кожного контуру з `contours[:CONTOURS_TO_CHECK]` пробувати кожен
epsilon з `APPROX_POLY_EPSILONS` по черзі, поки не отримаємо `len(approx) == 4` і
`_validate_document(...) == True`. Це знижує залежність результату від "магічного" одного
значення.

### 3.3 Sub-pixel уточнення кутів (cornerSubPix)

Після того, як 4 кути знайдено (у `_detect_corners_impl`, перед поверненням `corners_small`),
застосувати `cv2.cornerSubPix` для уточнення позицій:

```python
SUBPIX_WIN_SIZE = (5, 5)
SUBPIX_ZERO_ZONE = (-1, -1)
SUBPIX_CRITERIA = (cv2.TERM_CRITERIA_EPS + cv2.TERM_CRITERIA_MAX_ITER, 30, 0.01)

def _refine_corners_subpix(gray: np.ndarray, corners: np.ndarray) -> np.ndarray:
    pts = corners.reshape(-1, 1, 2).astype(np.float32)
    refined = cv2.cornerSubPix(gray, pts, SUBPIX_WIN_SIZE, SUBPIX_ZERO_ZONE, SUBPIX_CRITERIA)
    return refined.reshape(-1, 2)
```

Викликати після кожного успішного методу (`_try_adaptive_threshold`, `_try_canny`,
`_try_largest_contour`) перед поверненням з `_detect_corners_impl`. Обгорнути в `try/except`
(на однотонних ділянках `cornerSubPix` може кидати помилку) — при помилці повертати
неуточнені кути.

### 3.4 CLAHE перед бінаризацією (нерівне освітлення)

У `_try_adaptive_threshold` перед `cv2.GaussianBlur` додати опціональний крок CLAHE:

```python
CLAHE_CLIP_LIMIT = 2.0
CLAHE_TILE_GRID_SIZE = (8, 8)

def _apply_clahe(gray: np.ndarray) -> np.ndarray:
    clahe = cv2.createCLAHE(clipLimit=CLAHE_CLIP_LIMIT, tileGridSize=CLAHE_TILE_GRID_SIZE)
    return clahe.apply(gray)
```

Стратегія: спочатку пробувати без CLAHE (як зараз); якщо `_try_adaptive_threshold` і `_try_canny`
не знайшли кутів — повторити обидва методи на `_apply_clahe(gray)` перед переходом до fallback
(`_try_largest_contour`). Це додає "Спробу 1b/2b" у `_detect_corners_impl`.

### 3.5 (Опціонально, окремий under-задача) Hough-based fallback

Якщо після п.3.1–3.4 fallback (`_try_largest_contour`) теж не дає результату — додати
`_try_hough_lines(gray)`:
- `cv2.HoughLinesP` на Canny-краях;
- розділити лінії на ~горизонтальні/~вертикальні за кутом нахилу;
- взяти по 2 найдовші лінії з кожної групи, знайти 4 точки перетину;
- провалідувати через `_validate_document`.
Це **четверта** спроба, після bounding-box fallback. Якщо складно реалізувати надійно —
винести в окрему задачу низького пріоритету (Фаза 2.x), не блокувати інше.

### 3.6 Тести

Оновити/доповнити `tests/scenarios/test_perspective_auto.py` (зараз там лише каркас з TODO):

## ПРІОРИТЕТ 5 — Адаптивний HDR для фото-документів (Фаза 2.1)

**Проблема**: поточний `processing/hdr.py` добре працює для звичайних фото, але для
"документ-фото" (текст на світлому фоні) додає чорний відтінок у світлих ділянках —
шкідливо для друку.

### Кроки

1. **Детектор текстових/однотонних областей** — новий модуль `processing/text_mask.py`:
   ```python
   def text_region_mask(gray: np.ndarray) -> np.ndarray:
       """
       Повертає бінарну маску (uint8, 0/255) ділянок, схожих на текст:
       висока локальна щільність контрастних дрібних деталей.
       Підхід: адаптивна бінаризація + морфологічна фільтрація дрібних компонент.
       """
   ```
2. **Адаптивний HDR** у `processing/hdr.py` — нова функція
   `apply_adaptive(image, strength, text_mask=None)`:
   - Обчислює звичайний HDR-результат (як зараз).
   - У зонах, де `text_mask == 255`, зменшує ефект HDR (наприклад,
     `result = cv2.addWeighted(hdr_result, alpha, image, 1-alpha, 0)` з `alpha` меншим там,
     де є текст — реалізувати через поелементне змішування за маскою:
     `np.where(mask_3ch, blended_low, hdr_result)`).
3. **Pipeline**: у `run_autofix`, для `DocType.PHOTO`, якщо документ класифіковано як
   "фото документа" (потрібен додатковий прапорець від `doc_classifier`, наприклад
   `is_document_like: bool`, що вже частково реалізований через edge density/Hough lines —
   перевірити `processing/doc_classifier.py`), використовувати `hdr.apply_adaptive` замість
   `hdr.apply`.
4. **Налаштування**: `adaptive_hdr_enabled: bool` (за замовчуванням `True` для PHOTO+document-like),
   додати в `app_settings.py` і у `settings_window.py`.

### Критерії приймання

- На фото документа (текст на світлому папері, знято при поганому світлі) після Auto Fix
  світлі ділянки навколо тексту не темніють (порівняти середню яскравість фону до/після —
  різниця не повинна перевищувати X% від еталону, визначити X емпірично на тестовому наборі).
- На звичайному фото (без тексту) результат `apply_adaptive` практично не відрізняється від
  поточного `apply`.

## ПРІОРИТЕТ 7 — Оптимізація пам'яті (Фаза 2.3)

1. **Профілювання** — написати скрипт `tools/profile_memory.py`, що прогонює
   `BatchProcessor.run_auto` на черзі з N тестових зображень (N=10, 50, 100) з
   `tracemalloc`/`memory_profiler`, виводить пік пам'яті.
2. **Кешування прев'ю** — у `gui/preview.py` / `utils/image_utils.make_preview`: додати
   простий LRU-кеш (`functools.lru_cache` не підходить для np.ndarray — реалізувати власний
   словник `{path_or_id: preview_array}` з обмеженням розміру, наприклад 20 елементів).
3. **Обмеження черги завантажених зображень**: `BatchProcessor` зараз тримає лише шляхи
   (`_files: list[str]`), завантаження відбувається по одному файлу — перевірити, що жодне
   місце не тримає всі зображення черги одночасно в пам'яті (особливо в `gui/queue_view.py` —
   там, ймовірно, лише thumbnails). Якщо знайдено — додати explicit `del`/звільнення після
   обробки кожного файлу в `run_auto`.
4. **Streaming для дуже великих зображень** — окрема дослідницька задача (низький пріоритет
   у межах Фази 2): для зображень понад заданий розмір (наприклад > 4000px по довшій стороні)
   розглянути tile-based обробку для важких кроків (CLAHE, HDR). Це ризикована зміна — реалізувати
   в окремій гілці з benchmark "до/після" по якості та швидкості, не зливати без явного
   підтвердження користувача.
